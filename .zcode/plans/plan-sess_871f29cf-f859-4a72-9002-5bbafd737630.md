# Финальная интеграция: заменить legacy PipelineDsl.kt на чистый PipelineRunner

## Контекст проделанной работы

Pure-домен готов (PR 1–4, 7–9): `domain/pipeline/{Pipeline, Step, Stage, Side, Stop, Retry}.kt`, `domain/time/Clock.kt`, `infra/pipeline/{Interpreter, PipelineRunner}.kt`. 58 тестов зелёные, всё компилируется.

**Но новый пайплайн нигде не вызывается в проде.** Существующий `CrawlRunner.runUnsafe()` строит legacy `Pipeline` через `crawlPipeline { ... }` DSL, который содержит 90 строк кода, дублирующих новый `domain/pipeline/Pipeline.run()`. Spring-бин `createCrawlRunner()` падает с `NotImplementedError` при первом запуске.

### Шаг 3 — Переписать `crawl.kt` как thin Spring-фабрику `PipelineRunner`

Новый файл (`infra/runner/crawl.kt`):

```kotlin
class CrawlRunner(
    private val pipeline: ru.wbparser.domain.pipeline.Pipeline,
    private val registry: SideInterpreterRegistry,
    private val downloader: suspend (Crawling) -> Step<Crawling, Fetched>,
    private val db: DatabaseHandle,
) {
    val pipelineRunner = PipelineRunner(pipeline, registry)

    suspend fun run(): RunResult { ... } // unchanged flow: advisory lock → load targets → runner.run(tasks) → job row
}
```

Используя существующие beans:
- `KtorDownloader` / `PlaywrightDownloader` (`infra/http/*`) → адаптер в `Stage<Crawling, Fetched>` через `Step.Done(testFetched(task))`
- `parseWbCatalog` из `PipelineConfig.kt:27` → `Stage<Fetched, ParsedPage>` через `Step.Done(ParsedPage(...))`
- `enrich: Stage<ParsedItem, SavedItem> = { item -> Step.Done(SavedItem.from(item, targetId = ?)) }` — `targetId` приходит из `Crawling.targetId` через ParsedItem контекст (нужно протащить через `enrich` lambda: либо передавать `targetId` параметром в стадию через closure, либо хранить в `ParsedItem`)

**Решение по targetId:** enrichment stage получает `targetId` через closure: внутри `crawl.run()` перед каждым проходом читаем `task.targetId` и передаём его в `enrich = { item, targetId -> Step.Done(SavedItem.from(item, targetId)) }`. Это требует расширить `Pipeline.enrich` сигнатуру — добавить параметр или сделать стадию бинарной.

**Альтернатива (рекомендую):** оставить `enrich: Stage<ParsedItem, SavedItem>` как сейчас, но передавать `targetId` через контекстный `EnrichContext` который хранится в run-loop и достаётся через thread-local/closure. Самый чистый вариант — сделать `enrich` лямбдой вида `(item: ParsedItem, context: EnrichContext) -> Step.Done(SavedItem)`, обернуть в `Pipeline.enrich = Stage<ParsedItem, SavedItem>` где второй аргумент прибит closure к текущему `task.targetId`.

## Что НЕ делаем

- Не плодим новый DSL поверх `Pipeline` — конструктор `Pipeline(download = …, parse = …, …)` с лямбдами короче и понятнее.
- Не сохраняем `Session` / `CrawlStats` — удаляем.
- Не вводим concurrency back в pure-домен — последовательность остаётся в `Pipeline.run()`, параллелизм может быть сделан через несколько `runner.run()` вызовов снаружи.
- Не удаляем `StopReason` отдельно — после шага 2 импорт `StopReason` остаётся только в `crawl.kt` и `installCrawler.kt`, их тоже вычистим в шаге 3.

## Риски

| Риск | Митигация |
|---|---|
| `targetId` пропадает при обёртке стадии через closure | передаём `task.targetId` через closure в момент создания `pipeline.enrich` лямбды внутри `CrawlRunner.run()` per-target |
| `ScheduleRetry` Side нужно реально scheduler'ить, а не просто emit | отдельный `ScheduleRetryInterpreter` с `kotlinx.coroutines.delay(side.afterMs)` и повторным добавлением в task list |
| Поведение кравлера меняется (sequential vs concurrent) | фича-флаг `CrawlProperties.spider.concurrency` уважается в runner'е через `coroutineScope { tasks.map { async { runner.run(listOf(it)) } }.awaitAll() }` |
| Тесты Playwright/Ktor требуют реальный web | оставляем как есть — `@Tag("integration")` на тестах, по умолчанию они отключены |
