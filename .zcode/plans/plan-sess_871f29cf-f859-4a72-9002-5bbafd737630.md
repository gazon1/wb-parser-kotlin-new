## Что осталось

### 1. `BrowserPool` — 943 строки, следующий кандидат на дробление

Файл держал пять решений: клиент AdsPower API, Playwright-автоматизация, аренда профилей,
жизненный цикл профиля, состояние страницы. ADR
`2026-10-20-the-big-classes-are-split-by-decision` требует дробить по решению.

**Сделано в PR #68:** `BrowserPool` (пул) · `BrowserProfileState` (состояние профиля) ·
`AdsPowerApi` / `RealAdsPowerApi` · `BrowserAutomation` / `CdpAutomation` ·
`BorrowedPage` · `ChromeEndpointProbe` · `AdsPowerConfig` / `BrowserProfileConfig`.

Швы готовы были давно: `AdsPowerApi` и `BrowserAutomation` внедряются конструктором
(ADR `2026-10-17`), а `FakeAdsPowerApi` есть. `BrowserProfileStateTest` проверяет
состояние профиля напрямую — раньше это было возможно только через пул.

Осталось покрыть: `RealAdsPowerApi` (6 %) — HTTP-клиент к Local API, и `CdpAutomation`
(21 %) — сам Playwright. Первый тестируется через локальный HTTP-сервер (образец —
`KtorDownloaderTest`), второй — только настоящим Chrome.

### 2. Браузерный путь fetch не покрыт

`BrowserDownloader` — 14 %. Ошибка в нём выглядит как «каталог вернул 0 товаров», а не
как ошибка: страница пуста, счётчики нулевые, отчёт зелёный. Нужен хотя бы один тест
на реальном сокете — в репозитории уже есть такой образец (`KtorDownloaderTest`).

### 3. Гейт покрытия измерял не те классы

Исправлено 2026-10-20: строки floors меряются по merged-отчёту с фильтром по пакетам.
До этого отчёт модуля `app` показывал 35 классов как непокрытые (0 %), хотя merged-отчёт
показывал 57–100 %: тесты этих классов живут в модуле `tests`, а отчёт модуля их не видит.
Фloor `app` поднят с 31 % до 84 %.
