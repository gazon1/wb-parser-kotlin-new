# Egress measurement protocol — как проверить, по чему WB режет лимит

Протокол замера, который идёт **перед** любыми правками кода. Ответ на вопрос,
без которого вся работа бессмысленна: **по чему ключ лимита WB — по rate на IP,
по самому IP или по профилю?**

Суть: WB считает источник запросов **по IP**. Пока все профили AdsPower деплоя
выходят с одного IP, лимитер видит их суммарный поток, и делить трафик между
профилями бесполезно — ограничение не обходится профилями. Несколько IP дают
несколько независимых бюджетов.

Термины:

- **Egress-группа** — набор профилей AdsPower, выходящих с одного IP. Владеет
  rate limit'ом, circuit breaker'ом и долей антибот-бюджета.
- **Прокси** — настраивается в самом AdsPower, не в коде краулера. Конфигурация
  краулера только объявляет, какие профили ожидаются за одним IP; факт проверяет
  probe.

## 1. Протокол замера (PR 0) — выполнить ДО любых правок кода

Ответ на вопрос, без которого вся работа бессмысленна: **по чему ключ лимита WB
— по rate на IP, по самому IP или по профилю?**

### 1.1 Условия, без которых замер недействителен

| Правило | Почему |
|---|---|
| Фиксированный объём: ровно N запросов на прогон (`--count 40`) | Иначе объём выборки зависит от того, что мы измеряем |
| Пауза **30–60 мин** между прогонами на одном IP | У лимитера есть состояние (окно/репутация); A2 сразу после A1 наследует штраф и не измеряет ничего |
| Рандомизированный порядок прогонов в блоке на одном IP | Порядок не должен быть confound'ом |
| ≥3 повтора на прогон | Одна выборка в 40 запросов плохо различает 0 % и 5 % |
| Одно и то же окно суток для всех прогонов | Нагрузка на WB разная ночью и днём |
| Один и тот же каталог и страницы | Форма запроса не должна меняться |
| **Прокси того же класса, что и боевой** (residential против residential) | Вывод по датацентровому прокси к резидентному не переносится |
| **Свежий профиль под каждый новый IP** | Куки и fingerprint профиля привязаны к IP; перенос старого профиля на новый прокси сам по себе вызывает флаги |

### 1.2 Второй IP до закупки

Нужен всего один второй IP, и он не обязан быть платным:

- **триал резидентного прокси** — большинство провайдеров дают 1–3 IP сразу;
- **мобильная точка доступа / домашний Wi-Fi** — настоящий резидентный IP без
  закупки.

Боевые IP потом — того же класса, что и тестовые.

### 1.3 Прогоны

`--delay` — пауза между запросами **на этом IP**. 3.0 с ≈ текущий темп краулера
(`browser-min-request-interval-ms: 3000` + jitter).

| Прогон | Профиль(и) | IP | `--delay` | Что измеряет |
|---|---|---|---|---|
| **A0** | прод-конфигурация (несколько профилей, один pacer) | IP₁ | 3.0 | **baseline** — то, что работает сейчас; с ней сравниваются все критерии |
| **A1** | 1 профиль | IP₁ | 3.0 | доля отказов при одном профиле на одном IP |
| **A2** | 1 профиль | IP₁ | 6.0 | **тот же IP, вдвое ниже rate** |
| **A3** | **новый** профиль | **IP₂** | 3.0 | **тот же rate, другой IP** |
| **A4** | 1 профиль | IP₁ | 3.0 | контроль профиля: тот же IP, другой профиль |
| **A5** | 2 профиля, **разные IP** | IP₁ + IP₂ | 3.0 каждый | два IP одновременно |
| **A6** | 2 профиля, **один IP** | IP₁ | 3.0 каждый | **главный контроль**: вдвое больший rate на этот IP |

A5 и A6 — решающая пара: одинаковое число запросов и одинаковое число профилей,
различается только распределение по IP.

### 1.4 Команда

```bash
uv run scripts/wb_browser_fetch.py \
  --profile k18a6j35 \
  --catalog 15621 \
  --count 40 \
  --delay 3.0 \
  --label A1 \
  --warmup-delay 15 \
  --warmup-attempts 3 \
  --json > /tmp/exp/A1.json
```

**Прогрев — часть протокола, а не пауза перед измерением.**

WB отказывает холодной сессии: сессия, у которой не решён антибот-вызов, получает
498 на залп, даже если адрес чист. Измерение холодной сессии измеряет **вызов**, а
не адрес: цифры говорят о том, сколько занял антибот, а не о том, кто обращается.

Поэтому прогрев — это **проверка**: инструмент открывает страницу, ждёт
`--warmup-delay` секунд и делает один пробный запрос; если он отказал, прогрев
повторяется (до `--warmup-attempts` раз). Прогон, у которого сессия так и не
прогрелась, помечается `warmup_ok: false` и **измерением не считается**: его
отказы говорят о вызове.

Это не косметика. Первый блок выполнялся без такой проверки, с прогревом 3,5 с по
умолчанию, и его числа нельзя читать как свойство адреса: тот же профиль на том же
адресе с прогревом 15 с дал 0 отказов из 10, где с прогревом 3,5 с — 30 из 40.
Правка первого блока — в `docs/operations/egress-measurements/2026-10-20-block-1.md`.

Для A5 и A6 нужны два профиля — прогоны делаются по одному профилю каждый, но с
**разными** интервалами так, чтобы суммарный rate на IP был нужным:

- A5: два отдельных процесса, каждый со своим `--delay 3.0`, но **на разных IP**
  и **не одновременно** (иначе это не «2 IP по 3 с», а «1 IP с удвоенным
  трафиком»);
- A6: два отдельных процесса, каждый со своим `--delay 3.0`, **на одном IP**,
  одновременно.

### 1.5 Интерпретация

| Наблюдение | Вывод | Действие |
|---|---|---|
| **A2 ≪ A1** и **A3 ≈ A1** | лимит **rate-based на IP** | **Phase 1 работает**: N IP = N × бюджет. Идём в PR 1 |
| **A2 ≪ A1** и **A3 ≪ A1** | лимит **репутационно-сессионный** | Phase 1 работает, но IP надо **ротировать**, а не просто разделить ⇒ отдельный заход |
| **A2 ≈ A1** | лимит не rate-based | Phase 1 в текущем виде бессмысленна ⇒ **стоп** |
| **A5 ≈ A6** по доле и **A6 ≈ 2 × A5** по темпу | лимит **по профилю**, IP не ключ | **стоп** |
| **A5 лучше A6** по доле и **A5 ≈ 2 × A1** по темпу | лимит **по IP (агрегат)** | **Phase 1 работает.** Идём в PR 1 |

**Гейт:** идём в PR 1, если **A5 ≈ 2 × A1 по темпу** и доля отказов на A5 не хуже
A0/A1. Иначе останавливаемся и переписываем план.

### 1.6 Где смотреть долю отказов

`--json` печатает на stdout:

```json
{
  "label": "A1",
  "requests": 40,
  "refused": 15,
  "errored": 0,
  "succeeded": 25,
  "refusal_ratio": 0.375,
  "statuses": [200, 498]
}
```

`refusal_ratio` = `refused / requests`. Знаменатель обязателен: без него числитель
ничего не значит (см. `docs/decisions/2026-10-20-anti-bot-refusals-are-measured.md`).

## 2. Что дальше

По результатам замера открывается серия PR:

| PR | Что делает |
|---|---|
| PR 1 | egress-группы, per-group pacing, конфигурация, probe, метрики |
| PR 2 | per-group circuit breaker и роутер |
| PR 3 | состояние цели в БД: свежесть, классификация отказов, backoff |
| PR 4 | операционный runbook: прокси, профили, разбор метрик |

Операционная часть (создание профилей с прокси, разбор метрик, сброс backoff)
— в `docs/operations/egress-groups-runbook.md`, он появляется вместе с PR 4.

> **Правка 2026-10-21 (третья).** Порт протокола трактует отказ как ограничение
> **темпа** на адрес (§1.5). Данные репетиции перед блоком 2 этого не показывают:
> отказ приходит **по счёту запросов**, а не по темпу.
>
> Прогон 40 запросов, свежий профиль, сессия прогрета:
>
> ```
> 200 ×15 → 498 ×17 → 0 ×8
> ```
>
> Первые 15 запросов проходят, дальше WB режет сессию. Тот же профиль и адрес при
> **вдвое меньшем** темпе (6,0 с вместо 3,0) дают тот же порог (13 успешных) —
> темп на него не влияет. Сессия, которую однажды обрезали, остаётся обрезанной:
> следующий прогон по ней начинается с трёх успешных запросов.
>
> **Что из этого следует для протокола.** Инструмент измеряет долю отказов в
> залпе из 40 запросов, а залп всегда пересекает порог — значит, доля говорит о
> том, **где в залпе попал порог**, а не о свойстве адреса. Ни один блок,
> выполненный по нынешнему §1.3, не может ответить на вопрос §1.5.
>
> **Что измерять вместо.** Порог (на каком по счёту запросе пришёл первый отказ)
> и его восстановление (проходит ли порог после паузы 30–60 минут). Это вопрос о
> сессии, а не об адресе, — и он же отвечает на вопрос про «N IP = N бюджет»:
> если ограничение по счёту, то «бюджет» — это не запросы в минуту, а запросы
> до первого отказа, и «N адресов» означает N сессий, а не N потоок.
>
> Блок 2 в нынешнем виде запускать нельзя: он повторит ошибку блока 1, только
> аккуратнее. Инструмент должен измерять порог, а не долю.

## 4. Как выполнять блок

Правила §1.1 — это **исполняемый** протокол, а не список пожеланий: блок выполняется
скриптом `scripts/measure_egress.py`, и он же говорит, прошёл ли блок гейт.

```bash
# План блока: что меряем, на каких профилях и по каким адресам.
cat > /tmp/block.json <<'JSON'
{
  "block": "2026-10-21-block-2",
  "catalog": 15621,
  "query": "menu_v3_15621 карты памяти",
  "count": 40,
  "repeats": 3,
  "combat_class": "datacenter",
  "runs": [
    {"label": "A1", "profile": "<профиль на IP₁>", "address": "IP1", "delay": 3.0, "proxy_class": "direct"},
    {"label": "A3", "profile": "<профиль на IP₂>", "address": "IP2", "delay": 3.0, "proxy_class": "datacenter"}
  ]
}
JSON

# Пробный прогон: показывает порядок и паузы, ничего не меряет.
uv run python scripts/measure_egress.py --plan /tmp/block.json --dry-run

# Настоящий блок.
uv run python scripts/measure_egress.py --plan /tmp/block.json
```

Что делает скрипт:

- **порядок** прогонов рандомизируется с seed'ом, который записывается в блок, —
  порядок воспроизводим и не выбирается в момент прогона;
- **пауза** между прогонами на одном адресе (30–60 мин) держит часы, а не память
  оператора; `--pause-minutes 0` — только для репетиции, и такой блок гейт не проходит;
- каждый прогон пишет **время старта, адрес и класс** адреса, поэтому и паузу, и
  класс можно проверить потом, по данным, а не по отчёту;
- **отчёт пишется из данных**: числа в нём нельзя поправить рукой, не разойдясь с
  JSON рядом.

Скрипт возвращает ненулевой код, если блок не прошёл гейт, и пишет в отчёт таблицу
правил с честным «нет».

### Гейт на закоммиченных блоках

`scripts/check-egress-block.py` — гейт репозитория (`static`): он читает сырые JSON
каждого закоммиченного блока и держит его отчёт этим данным:

- числа в таблице прогонов — это числа из сырых JSON (сумма по повторам);
- правило, о котором отчёт говорит «да», должно быть подтверждено данными;
- вердикт блока должен согласовываться с правилами.

Правило, которое из данных **не решается** (каталог прогона, свежесть профиля),
гейт не считает выполненным: он так и пишет — «не решается из данных», а не «да».
