# Egress groups — операционный runbook

Как поднять краулер на **нескольких egress IP**, как это проверить и что делать,
когда что-то пошло не так.

Суть: WB считает источник запросов **по IP**. Пока все профили AdsPower деплоя
выходят с одного IP, лимитер видит их суммарный поток, и делить трафик между
профилями бесполезно — ограничение не обходится профилями. Несколько IP дают
несколько независимых бюджетов.

Термины:

- **Egress-группа** — набор профилей AdsPower, выходящих с одного IP. Владеет
  rate limit'ом, circuit breaker'ом и долей антибот-бюджета.
- **Прокси** — настраивается в самом AdsPower, не в коде краулера. Конфигурация
  краулера только объявляет, какие профили ожидаются за одним IP; факт проверяет
  probe.

Протокол замера, который идёт **перед** правками кода, — в
`docs/operations/egress-measurement-protocol.md`.

## 1. Подготовка

### 1.1 Прокси

Нужен **резидентный** (residential или mobile) прокси, а не датацентровый:
датацентровые адреса WB видит заранее, и весь смысл разделения теряется.

- **sticky** (фиксированный IP на сессию) — предпочтительно. Группа = один адрес,
  и «паузер на группу» действительно означает «паузер на адрес».
- **ротационный** — работать будет, но адрес меняется посреди работы: cookies
  сессии остаются привязаны к старому, а WB видит смену IP. Probe это покажет
  (`crawl.egress.ip.changes`), группа перебазируется, но часть запросов уйдёт
  в бан. Если прокси вынужденно ротационные — это отдельный заход, не этот.

Проверить, что адрес действительно резидентный: открыть `https://api.ipify.org`
через сам прокси и посмотреть, что вернулось. Датацентровый диапазон виден сразу.

### 1.2 Трафик

Обход — **132 цели × 5 страниц = 660 запросов**. Запрос — это `fetch()` внутри
Chrome, то есть **только JSON-ответ WB**; полный рендер страницы с картинками не
качается (навигация — один раз на профиль). Оценка: **~0,05–0,15 GB на полный
обход**. Десять обходов в сутки — единицы гигабайт. Трафик не блокер закупки;
решают качество адреса и цена.

### 1.3 Профили

Активных профилей в AdsPower — 5, в конфигурации краулера — 3. Для N групп нужны
**новые** профили.

**Старый профиль не переносится в группу с прокси.** Cookies и fingerprint
профиля привязаны к адресу, с которого он долго ходил; переключение на новый
прокси само по себе вызывает флаги. Порядок:

1. создать прокси у провайдера;
2. создать профиль в AdsPower **сразу с этим прокси** — прокси задаётся при
   создании, и менять его у живого профиля нельзя;
3. прогреть профиль: открыть каталог WB, дождаться anti-bot челленджа;
4. вписать `profile_id` в `crawler.spider.egress-groups`.

Через MCP-тулы это `create-proxy` → `create-browser` с `user_proxy_config`;
через CLI — `adspower-browser`.

### 1.4 Конфигурация

```yaml
crawler:
  spider:
    egress-groups:
      - id: ip-1
        profiles: [k18a6v75]
        pacing: {min-interval-ms: 3000, jitter-min-ms: 200, jitter-max-ms: 500}
      - id: ip-2
        profiles: [k17bnqsi]
        pacing: {min-interval-ms: 3000, jitter-min-ms: 200, jitter-max-ms: 500}
```

**Один профиль на группу** — оптимум по пропускной способности: бюджет группы
задаёт паузер (1 запрос в ~3 с на IP), а не число профилей. Два-три профиля на
группу дают не скорость, а живучесть при 2-минутном cooldown'е: пока один
профиль отдыхает, IP продолжает работать.

Группы — **единственный** список профилей. Ключ `crawler.spider.browser-profiles`
удалён: два списка, которые должны совпадать, — это один список лишнего, и день, когда
они разойдутся, наступит сам.

`target-concurrency` выводится из числа профилей. Задавать руками не нужно: паузер
и так ограничивает поток, а лишние воркеры только стоят в очереди.

## 2. Что делает probe

При старте и потом раз в `crawler.spider.egress-probe-interval-ms` (15 минут по
умолчанию) краулер открывает IP-echo **через профиль** и сравнивает фактические IP.
До первого запроса к WB проверяется и объявление: прокси каждого профиля читаются
у AdsPower, и группы проверяются на «одна группа — один прокси, разные группы —
разные прокси». Probe, который не смог выполниться, — это предупреждение: он никогда
не останавливает краулер.

| Проверка | Результат |
|---|---|
| IP внутри группы различаются | **FAIL на старте** — конфигурация врёт, группу нельзя пацить как один источник |
| IP между группами совпадают | WARN, `crawl.egress.isolated=0` — изоляция фиктивна |
| профили одной группы за разными прокси | **FAIL на старте** — группа не одна группа |
| две группы за одним прокси (или обе без прокси) | **FAIL на старте** — это один адрес и один бюджет, а не два |
| IP группы изменился | WARN, `crawl.egress.ip.changes++`, группа перебазируется (новый IP = новый бюджет) |
| эхо-сервисы недоступны | WARN, `crawl.egress.probe.failed=1`, старт **не** блокируется |

Поле `ip` в ответе AdsPower — **записанное** значение, а не живой probe;
ориентироваться на него нельзя.

Сделать предупреждение ошибкой запуска: `require-isolated-egress-groups: true`.

### Что значит «сменился адрес»

Сменившийся адрес — это **новая личность**, а не тот же адрес с другим IP:

- circuit группы закрывается — отказы старого адреса не запрещают новому;
- книги группы (счётчики, окно здоровья) обнуляются;
- штраф адреса (`egress_failure_count`) снимается с целей, которые обслуживал этот
  адрес: виноват был адрес, которого больше нет.

Прогон каждой цели оставляет строку — она и есть «кто обслуживал»:

```sql
SELECT started_at, egress_group, egress_ip, outcome, pages, items
  FROM crawl_target_runs
 ORDER BY started_at DESC
 LIMIT 50;
```

`outcome` — один из `ok`, `antibot`, `target_candidate`, `error`.

## 3. Метрики

| Метрика | Что показывает |
|---|---|
| `crawl.egress.pages` | успешных страниц/час по группе — **целевая метрика** |
| `crawl.egress.refusals{kind}` | отказы по группе: `kind="antibot"` — ответ WB, `kind="transport"` — запрос не дошёл |
| `crawl.egress.requests` | запросов по группе — знаменатель доли отказов |
| `crawl.egress.pacer.wait` | группа упирается в rate limit (растёт время ожидания) |
| `crawl.egress.circuit.state` | 0 closed / 1 half-open / 2 open — антиботная цепь группы |
| `crawl.egress.transport.suspended` | 1 — транспортная цепь группы отдывает (сеть, а не адрес) |
| `crawl.egress.isolated` | 1 — группа реально изолирована по IP, 0 — нет |
| `crawl.egress.ip.changes` | сколько раз IP группы менялся |
| `crawl.egress.all_down` | все группы были недоступны одновременно |

Два вида отказа — разные счётчики внутри одного, и они разные вещи:

- `kind="antibot"` — WB ответил 498/403/401. Это про **сессию**: запросы считаются у
  сессии (профиля), и она отдывает.
- `kind="transport"` — запрос не дошёл или ответ не пришёл. Это про **сеть**: адрес
  тут ни при чём, и антиботная цепь из-за него не открывается.

Доля отказов по группе в PromQL:

```promql
sum by (egress_group) (rate(crawl.egress.refusals{kind="antibot"}[15m]))
/
sum by (egress_group) (rate(crawl.egress.requests[15m]))
```

Транспортные сбои считаются отдельно и **не входят** в этот знаменатель:

```promql
sum by (egress_group) (rate(crawl.egress.refusals{kind="transport"}[15m]))
```

**Целевые значения** (N групп, baseline — один IP):

> **Оговорка (2026-10-21).** Эта таблица исходит из модели «N адресов = N × бюджет».
> Замер 2026-10-20 её **не подтвердил**: два адреса одновременно дали 22.5 % отказов
> против 2.5 % у одиночного адреса, а тот же профиль на том же адресе под нагрузкой
> соседа отказал в 32.5 % — то есть второй адрес не дал «чистого» бюджета, он дал
> общий. До второго блока (≥3 повторов, ADR
> `2026-10-27-the-measurement-does-not-authorize-a-second-address`) эти критерии —
> гипотеза, а не измеренная норма.

| Проверка | Критерий | Допуск |
|---|---|---|
| успешных страниц/час | ≥ N × baseline | ≥ 0,75 × N × baseline |
| доля отказов на группе | не хуже baseline | не хуже baseline + 2 п.п. |
| время полного обхода | ≤ baseline / N | × 1,2 |

### Пороги: фон, тревога, авария

Число — это то, при котором человеку надо что-то делать. «Посмотреть на метрику» — не
порог.

> **Числа ниже — ориентир, а не измерение (2026-10-21).** Порог «< 5 % / > 10 % /
> > 25 %» за 15 минут был написан до замера. Замер 2026-10-20 показал разброс от
> 2.5 % до 77.5 % отказов в одном вечере на одном адресе: 15-минутное окно в таком
> разбросе ничего не различает, и число нельзя назвать порогом, пока не сказано, что
> считается нормой. Пересчёт — вместе со вторым блоком замера.

| Метрика | Фон | Тревога | Авария | Действие |
|---|---|---|---|---|
| доля отказов за 15 мин | < 5 % | > 10 % | > 25 % | поднять `min-interval-ms` группы; при аварии — сменить прокси |
| `crawl.egress.circuit.state` | 0 | 2 (open) | 2 дольше 10 мин | адрес не отвечает: сменить прокси, проверить, жив ли он |
| `crawl.egress.transport.suspended` | 0 | 1 | 1 дольше 5 мин | сеть до адреса лежит: адрес тут ни при чём, чинить надо маршрут |
| `crawl.egress.isolated` | 1 | 0 | 0 у всех групп | изоляции нет: две группы за одним адресом, бюджет один |
| `crawl.egress.ip.changes` | 0 | > 0 за час | > 0 за сутки | прокси ротационный: sticky-IP у провайдера, иначе адрес меняется быстрее, чем успевает остыть |
| `crawl.egress.all_down` | 0 | > 0 | > 0 два раза подряд | все адреса лежат: прогон не начнётся, пока не откроется хотя бы один circuit |
| `crawl.egress.probe.failed` | 0 | > 0 | > 0 постоянно | эхо-сервис недоступен: адрес неизвестен, изоляция не подтверждена |
| `crawl.egress.pacer.wait` | ≈ 0 | растёт | растёт линейно | группа упирается в rate limit: поднять `min-interval-ms` |

### Ёмкость считается в сессиях, а не в адресах

Адрес без живой сессии ничего не отправляет, а сессия, которую WB отказала, не
отправляет тоже. Поэтому ёмкость краулера — это число **живых сессий**, и оно
показывается рядом с группами:

```bash
curl -s localhost:8080/api/health/ready | jq .egress.sessions
```

```json
{
  "live": 3,
  "retired": 1,
  "sessions": [
    {"profile": "k18a6j35", "group": "direct", "state": "warm",
     "requests": 42, "refusals": 2, "answered": 40, "age_ms": 918000}
  ]
}
```

- `live` — сколько сессий ещё могут работать. Это и есть ёмкость.
- `retired` — сколько сессий вышло из ротации.
- `requests` / `refusals` — счётчики сессии: сколько запросов она отправила и сколько
  из них WB отказал. **Это и есть то, что измеряет счётчик WB**: по замеру
  2026-10-21 порог отказа — порядка 10–15 запросов на сессию, и темп на него не
  влияет.

> **Ключ счётчика ещё не установлен (2026-11-03).** Замер не развёл «счётчик живёт в
> профиле» и «счётчик живёт в адресе»: оба объясняют все прогоны репетиции. Поэтому
> счётчики ведутся **и у сессии, и у группы**, и ledger хранит оба. Пока разведка не
> сделана, лимиты сессии выключены (`requests-per-session: 0`), и решение «профиль
> выводится навсегда» не принято.

### Что лежит в ledger'е

Прогон каждой цели оставляет строку — и в ней теперь **и адрес, и сессия**:

```sql
SELECT started_at, egress_group, egress_ip, session_id,
       session_requests, session_refusals, outcome
  FROM crawl_target_runs
 ORDER BY started_at DESC
 LIMIT 50;
```

- `session_id` — профиль, чья сессия обслужила прогон;
- `session_requests` — сколько запросов эта сессия отправила к моменту прогона;
- `session_refusals` — сколько из них WB отказал.

Отдельно — «последнее здоровье» адреса:

```sql
SELECT group_id, egress_ip, probed_at, last_healthy_at
  FROM crawl_egress_groups;
```

`last_healthy_at` — момент, когда группа **отвечала нормально**. Без него
«адрес сменился» и «адрес замолчал» выглядят в таблице одинаково, а это ровно то
различие, которое показал замер: разброс внутри одного адреса больше разброса между
адресами. Пишет его краулер (успешный прогон), а `probed_at` — проба (адрес).

### Health-эндпоинт

`GET /api/health/ready` отвечает разделом `egress` — по каждой группе: адрес (из
леджера, а не из метрики), изолирована ли она, состояние circuit'а, запросы, отказы и
время ожидания паузера. Это то, что смотрит человек, когда метрики уже показали
проблему.

```bash
curl -s localhost:8080/api/health/ready | jq .egress
```

## 4. Состояние целей и back-off

Цель, ушедшая в back-off, видна так:

```sql
SELECT id, name, consecutive_failures, egress_failure_count,
       next_attempt_at, last_crawled_at, anomaly_group
  FROM crawl_targets
 WHERE next_attempt_at IS NOT NULL
 ORDER BY next_attempt_at;
```

Два счётчика, и их нельзя путать:

| Счётчик | Растёт от | Back-off | Кап |
|---|---|---|---|
| `consecutive_failures` | цель виновата: ответ не похож на каталог | 30 мин → 1 ч → 2 ч → … | 24 ч |
| `egress_failure_count` | виноват адрес: 498, circuit открыт, профили заняты | 15 мин → 30 мин → 1 ч | 2 ч |

Аномалия, которая выглядит как «не каталог», **не штрафует цель сразу**: если
группа, которая её принесла, отказывает (доля отказов выше 10 % за 10 минут) —
это, скорее всего, выгоревший адрес, и цель просто переочередится. Штраф
ставится, когда аномалию подтвердила другая группа или когда группа отвечает
нормально.

Сбросить штраф цели:

```sql
UPDATE crawl_targets
   SET consecutive_failures = 0,
       egress_failure_count = 0,
       next_attempt_at = NULL,
       anomaly_group = NULL
 WHERE id = '<target-uuid>';
```

## 5. Что делать, когда что-то не так

| Симптом | Причина | Действие |
|---|---|---|
| `crawl.egress.isolated=0` у всех групп | все профили без прокси ⇒ один IP | задать прокси в AdsPower и завести новые профили |
| `crawl.egress.isolated=0` у одной группы | два разных прокси выходят с одного адреса | другой прокси для этой группы |
| `crawl.egress.ip.changes` растёт | прокси ротационный | sticky-IP у провайдера, либо принять как есть |
| `crawl.egress.pacer.wait` большой | IP упирается в rate limit | поднять `min-interval-ms` для этой группы |
| `crawl.egress.circuit.state=2` долго | IP сгорел | пауза 30 с + half-open; если не восстановился — другой IP |
| `crawl.egress.all_down` растёт | все адреса сгорели одновременно | пауза цикла; проверить прокси |
| `crawl.egress.probe.failed` растёт | эхо-сервисы недоступны | проверить сеть; на работу краулера не влияет |
| профили в группе ведут себя по-разному | один из них не за тем прокси | probe покажет расхождение внутри группы — FAIL на старте |
| `consecutive_failures` растёт у одной цели | цель действительно не читается | посмотреть `anomaly_group`; если группа была больной — сбросить штраф |
