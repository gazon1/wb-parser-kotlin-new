# Camoufox через VPS-прокси — локальный запуск и throughput (2026-11-15)

Замер к issue #267: проверена целевая схема **до** правок production-кода — парсер и
Camoufox локально, VPS как proxy endpoint.

Сырые JSON — рядом, в `raw/`; числа ниже из них. Прогоны сняты harness'ом до двух
правок, описанных в §«Ограничения» (429 и каталог профилей), поэтому один-в-один
текущим `scripts/camoufox_bench.py` они не повторяются — повторяется протокол, а не
артефакт.

## Что показали числа

**Пропускная способность растёт с числом профилей до трёх, дальше не растёт.** Прямой
адрес: 1362 / 2387 / 3952 товаров/мин на 1–3 профилях (1,00 / 1,75 / 2,90) и 3473 на
четырёх — уровень 4 **ниже** уровня 3. Через прокси: 1244 / 2052 / 3080 на 1–3 профилях
(1,00 / 1,65 / 2,48) и 3814 на четырёх (3,07).

**Уровень 4 на прямом адресе оборвался отказом.** Один профиль получил 498 на 11-м
запросе, и по правилу «остановка на первом отказе» остальные остановились, не дойдя до
20 запросов (9–11 каждый). Его `товаров/мин` посчитан по ~69 с работы вместо полного
окна, поэтому с уровнем 3 он напрямую не сравним. Это цена правила остановки, а не
дефект: после отказа продолжать бессмысленно, но и ряд получается короче.

**Прокси добавляет ~120–160 мс к медиане, но пропускную способность съедает хвост.**
p50 на прямом адресе — 211–241 мс, через VPS — 336–390 мс; разница устойчива на всех
четырёх уровнях. Медиана объясняет не всё: на трёх профилях 60 запросов через туннель
заняли 52,6 с суммарного времени ответа против 15,2 с напрямую, и 27,5 с из этой разницы
— пять запросов по 2,6–9,3 с. Поэтому и прогон целиком длился 117 с против 91 с, а
товаров в минуту вышло 3079,6 против 3951,7 при одинаковом объёме (20 запросов на
профиль). При четырёх профилях дороже секунды были шесть запросов из 56, самый долгий —
13,8 с. Сколько из этого хвоста даёт VPS, а сколько SSH-туннель, здесь не разделено:
danted на втором VPS не стоял (§«Ограничения»).

**Первый отказ ложится на 11–18-й запрос.** Прямой адрес: 18-й (два профиля), 11-й
(четыре). Через прокси: 15-й (два профиля), 15-й (четыре). При трёх профилях отказов не
было ни на одном адресе за 60 запросов.

Это **согласуется** с гипотезой «WB считает запросы сессии», но её **не доказывает**:
во всех прогонах пауза одна и та же (3,0 с), поэтому вклад частоты и вклад счёта не
разделены. Числа первого отказа к тому же не монотонны по числу профилей, а на уровень
приходится один повтор — шум не отделён от эффекта. Чтобы разделить счёт и темп, нужен
прогон с другим `--delay` при том же объёме: это отдельный блок.

**Датацентровый адрес не отвергается на уровне API.** Через 46.29.162.175 HTML-переход
на каталог отвечает 498, а API из страницы — 200 и 100 товаров. Это подтверждает
правило umbrella-issue: статус навигации и доступность API — разные сигналы.

**Ресурсы — предел, который наступает раньше отказов.** RSS ≈ 1,6 ГБ на профиль
(1592 / 3532 / 4944 / 6741 МБ на 1–4 профилях), CPU — 52–224 с за 70–120 с прогона.
Четыре профиля — это ~6,7 ГБ и около двух ядер на этой машине.

**Профиль, который не открыл страницу, не считается измеренным.** В промежуточном
прогоне несколько профилей получили `NS_ERROR_NET_TIMEOUT` на навигации; такие записи
сохранены с `error` и выведены из `profiles_measured`, чтобы уровень не выглядел
полнее, чем был.

## Ограничения этого замера

- **Один прокси-адрес и он датацентровый.** Резидентного прокси нет: замер не отвечает
  на вопрос о боевом классе адресов, и доля отказов отсюда не переносится.
- **Один повтор на уровень**, и `user_data_dir` не сбрасывались между уровнями. Уровни
  сравнимы по **пропускной способности**; по **доле отказов** — нет.
- **Каталоги профилей не разведены по адресам.** Все прогоны шли из каталога по
  умолчанию (в артефактах `--profiles-dir` не записан), поэтому уровни через прокси
  могли стартовать на `profile-N`, где уже лежали cookies и storage прямого адреса, —
  то есть на сессии, которая переехала на другой адрес. Это ровно то, что запрещает
  правило «один профиль — один адрес — один отпечаток», и числа отказов через прокси
  поэтому не чистые: первый отказ мог прийти раньше из-за перенесённой сессии. Harness
  исправлен после прогонов (каталог называется по адресу, чужой адрес отвергается), но
  сами артефакты этим не переснять.
- **429 в этих прогонах не встретился**, и harness тогда его не останавливал. Сейчас
  429 останавливает профиль отдельным счётчиком (`throttled`), не складываясь с 498:
  «темп слишком высок» и «счётчик сессии потрачен» — разные ответы, и в крауле у них
  разные причины (`rate_limited` / `antibot`).
- **Темп не варьировался** (везде 3,0 с), поэтому счёт против rate не разделён. Это
  главное, чего замер не умеет: вывод «WB считает запросы сессии» остаётся гипотезой.
- **Уровни 3–4 неполные по объёму:** остановка на первом отказе обрывает соседние
  профили, поэтому `товаров/мин` считается по короче окну и не совпадает по объёму с
  уровнями 1–2.
- **`headless="virtual"` не проверен:** на машине нет `Xvfb`, установка требует sudo.
- Замер снят в одно окно суток, каталог один.
- Второй VPS (46.29.162.175) не имеет установленного danted — доступ шёл через
  SSH-туннель. Это транспорт замера, а не production-схема.

## Идентичность persistent-профиля — главная находка

`user_data_dir` сам по себе **не** сохраняет отпечаток. Запуск одного и того же каталога
дважды без указания `fingerprint`/`fingerprint_preset` дал **разные** identity: UA
(Mac / Windows), platform, screen, WebGL vendor и renderer — всё сменилось.

`fingerprint_preset=True` тоже рандомизирует: он выбирает случайный пресет при каждом
запуске, и осталась расходиться только ширина экрана (1366×768 против 1707×960).

Стабильность даёт **только явный preset-dict**: два запуска с одним и тем же JSON
совпали по всем полям (`stable: true`). Значит, отпечаток — это **данные профиля**,
которые надо посчитать один раз и хранить, а не то, что Camoufox сохранит сам.

## Прокси: что поддерживает Playwright

**SOCKS5 с логином и паролем браузер не принимает.** `playwright firefox
launch_persistent_context` падает с `Browser does not support socks5 proxy
authentication`. Проверено на реальном endpoint.

**HTTP-прокси с Basic-auth принимает.** Отдельная проверка с локальным CONNECT-прокси,
требующим `Proxy-Authorization`: браузер сначала пробует без учётных данных, получает
`407`, повторяет с ними и получает `200`.

## Запуск из Java — без Python-обёртки

Проверено, что Camoufox запускается **сырым** Playwright, без пакета `camoufox`:
`firefox.launch(executable_path=camoufox-bin, headless=True, env={CAMOU_CONFIG_1: …})`
даёт `navigator.webdriver=false`, подменённые UA/platform/screen и **200 + 100 товаров**
от API из страницы.

Весь конфиг — это путь к бинарю, `CAMOU_CONFIG_<n>` (JSON, нарезанный по 32767 байт),
`CAMOU_PREFS_<n>` и `FONTCONFIG_FILE`. Python в рантайме не нужен.

## Лицензия и установка

- Python-пакет `camoufox` — **MIT**. Сам браузер — **MPL-2.0** (README пакета).
- Бинарь ставится `uv tool install camoufox` + `camoufox fetch`; активная сборка
  пишется в `~/.cache/camoufox/config.json` (`active_version`). Пин — эта строка.
- Вес: сборка `158.0.1-beta.41` — отдельный Firefox, ~2,4 ГБ распакованного.

## Как повторить

```bash
# Прямой адрес, один профиль
uv run --with camoufox python scripts/camoufox_bench.py \
  --profiles 1 --count 20 --delay 3.0 --shared-address --out /tmp/direct-p1.json

# Через egress-адрес: SOCKS5 без пароля (туннель) или HTTP с Basic-auth
ssh -N -D 127.0.0.1:1082 root@<egress-host>
uv run --with camoufox python scripts/camoufox_bench.py \
  --profiles 4 --count 20 --delay 3.0 --shared-address \
  --proxy socks5://127.0.0.1:1082 --out /tmp/proxy-p4.json
```

Каталог профилей по умолчанию — `/tmp/camoufox-bench/<адрес>` (`direct` или
`proxy-<хост>-<порт>`), поэтому прямой и прокси-прогон не делят `user_data_dir`.
Каталог, уже принадлежавший другому адресу, отвергается: переезд объявляется явно,
`--allow-address-change`. Учётные данные прокси (HTTP Basic-auth) в имя каталога, в
маркер и в JSON не пишутся — остаются схема, хост и порт.

## Что не проверено и переносится в #268–#271

- Доля отказов на **резидентном** прокси и на боевом классе адресов.
- Разделение «счёт против rate»: нужен прогон с другим `--delay` при том же объёме.
- `headless="virtual"` и `virtual-gpu`.
- Долгая нагрузка (часы) и поведение при **устойчивом** 429/498: harness останавливается
  на первом 429, поэтому длительное ограничение темпа им не измеряется.
- Хвост задержки через прокси: нужен прогон на danted/HTTP-прокси, чтобы отделить VPS
  от SSH-туннеля этого замера.
- Повторный запуск профиля с сохранённым preset-dict **через прокси**.
- geoip-режим: без `geoip=True` Camoufox предупреждает, что при прокси его рекомендует.
