# Camoufox через VPS-прокси — локальный запуск и throughput (2026-11-15)

Замер к issue #267: проверена целевая схема **до** правок production-кода — парсер и
Camoufox локально, VPS как proxy endpoint. Отвечает на вопросы, без которых #268–#271
пришлось бы писать вслепую.

Сырые JSON — рядом, в `raw/`; числа ниже из них, а не из пересказа.

## Что показали числа

**Пропускная способность растёт почти линейно до 4 профилей.** Прямой выход:
1439 → 2771 → 3322 → 4584 товаров/мин, то есть 1,00 / 1,93 / 2,31 / 3,19 от одного
профиля. Через прокси: 1277 → 2443 → 3733 → 4347, то есть 1,00 / 1,91 / 2,92 / 3,40.
Прирост покупается не адресами, а параллелизмом браузеров: адрес на всех уровнях
один и тот же.

**Прокси не добавляет задержки.** p50 — 209–229 мс на прямом выходе и 214–226 мс через
VPS; разница внутри разброса. Хоп до VPS не заметен на фоне времени ответа WB.

**Отказы приходят пачкой и по счёту, а не по темпу.** Как только отказ начался, он идёт
подряд — поэтому воркер и останавливается после трёх. Первый отказ ложится на 9–19-й
запрос сессии, и с ростом числа профилей на одном адресе сдвигается раньше: 19-й при
одном профиле через прокси, 18-й при двух, 16-й при трёх, 13-й при четырёх. Это тот же
вывод, что и в замере 2026-10-21 (`docs/operations/egress-measurement-protocol.md`,
«Правка третья»): WB считает **запросы сессии**, а не темп.

**Датацентровый адрес не отвергается на уровне API.** Через 91.188.212.39 HTML-переход
на каталог отвечает 498, а API из страницы — 200 и 100 товаров. Это подтверждает
правило umbrella-issue: статус навигации и доступность API — разные сигналы. Замер
`direct-p1` — единственный прогон без единого отказа за 20 запросов, но отказы на
`proxy-p1` (2 из 20, первый на 19-м) приходятся на конец сессии, а не на её начало.

**Ресурсы линейны и предсказуемы.** RSS ≈ 1,05 ГБ на профиль (1,0 / 2,1 / 3,3 / 4,4 ГБ
на 1–4 профилях), CPU — 24–104 с за ~85 с прогона, то есть 0,3–1,2 ядра на 1–4
профиля. Четыре профиля — это ~4,4 ГБ и ~1,2 ядра: машина держит заметно больше, чем
четыре, и упирается не в железо.

**Решающая пара A5/A6 повторила прошлый результат по направлению.** Два профиля на
одном адресе: 6 отказов из 38 (15,8 %). Два профиля на двух адресах: 3 из 33 (9,1 %).
Направление то же, что в блоке 2026-10-20 (56,25 % против 22,5 %), но на этих объёмах
разница не отделима от шума: 3 против 6 отказов — это одна пачка, а не эффект.

## Ограничения этого замера

Указаны явно, потому что на них нельзя опираться.

- **Только один прокси-адрес.** Второй объявленный endpoint (`212.192.12.56`,
  `~/Caddy-vps/inventory/egress.local.yml`) был недоступен в момент замера: закрыты и
  22, и 1080. Решающая пара поэтому — «прямой адрес против VPS», а не «два VPS».
- **Прокси-адрес датацентровый, протокол требует резидентного.** Правило §1.1
  протокола не выполнено; вывод про долю отказов на боевом классе адресов не следует.
- **Меньше трёх повторов.** Каждый уровень прогнан один раз. Разброс между прогонами
  (proxy-p3 дал 5,2 % там, где proxy-p2 — 15,0 %) — это и есть шум, и он больше
  измеряемых различий между адресами.
- **Сессия не сбрасывалась между уровнями.** `user_data_dir` одни и те же, поэтому
  счётчик запросов сессии копился от прогона к прогону: `proxy-p4` мог получить первые
  отказы раньше `proxy-p1` именно поэтому, а не из-за четырёх профилей. Уровни
  сравнимы по **пропускной способности**, но не по **доле отказов**.
- **Замер снят в одно окно суток**, каталог один.
- **`headless="virtual"` не проверен:** на машине нет `Xvfb` (`which Xvfb` пуст), а
  пакет ставится только с паролем sudo. Режим `True` прошёл, `virtual` оставлен
  открытым вопросом.

## Идентичность persistent-профиля — главная находка

`user_data_dir` сам по себе **не** сохраняет отпечаток. Запуск одного и того же каталога
дважды без указания `fingerprint`/`fingerprint_preset` дал **разные** identity: UA
(Mac / Windows), platform, screen, WebGL vendor и renderer — всё сменилось.

`fingerprint_preset=True` тоже рандомизирует: он выбирает случайный пресет при каждом
запуске, и осталась расходиться только ширина экрана (1366×768 против 1707×960).

Стабильность даёт **только явный preset-dict**: два запуска с одним и тем же JSON
совпали по всем полям (`stable: true`). Значит, отпечаток — это **данные профиля**,
которые надо посчитать один раз и хранить, а не то, что Camoufox сохранит сам.

Это прямо влияет на #269 («не генерировать fingerprint заново при каждом запуске
профиля») и #270: без сохранённого preset-файла на профиль каждый рестарт выглядит как
новый браузер с того же адреса.

## Прокси: что поддерживает Playwright

**SOCKS5 с логином и паролем браузер не принимает.** `playwright firefox
launch_persistent_context` падает с `Browser does not support socks5 proxy
authentication` — это ограничение Playwright, а не Camoufox. Проверено на реальном
endpoint.

**HTTP-прокси с Basic-auth принимает.** Отдельная проверка с локальным CONNECT-прокси,
требующим `Proxy-Authorization`: браузер сначала пробует без учётных данных, получает
`407`, повторяет с ними и получает `200`. То есть HTTP-прокси — рабочий путь для
аутентифицированного endpoint, SOCKS5 — только без пароля.

Проверенный путь для замера: `ssh -N -D 127.0.0.1:1081 user@vps` даёт
неаутентифицированный локальный SOCKS5 с тем же egress IP — именно так сняты все
`proxy-*` прогоны. Это обход для замера, а не production-решение. Для боевой схемы есть
три варианта, и выбор между ними — в ADR:

- перевести danted на `socksmethod: none`, сохранив `client pass from <адрес>/32` —
  ограничение по адресу уже задано самим прокси, и пароль его не добавляет;
- поднять HTTP-слушатель с Basic-auth (проверено: работает);
- поднимать туннель из приложения.

## Запуск из Java — без Python-обёртки

Проверено, что Camoufox запускается **сырым** Playwright, без пакета `camoufox`:
`firefox.launch(executable_path=camoufox-bin, headless=True, env={CAMOU_CONFIG_1: …})`
даёт `navigator.webdriver=false`, подменённые UA/platform/screen и **200 + 100 товаров**
от API из страницы.

Вся «магия» пакета — это подготовка launch options: путь к бинарю, JSON конфига,
нарезанный на `CAMOU_CONFIG_<n>` (по 32767 байт), prefs в `CAMOU_PREFS_<n>` и
`FONTCONFIG_FILE`. Ничего из этого не требует Python в рантайме. Значит, вариант
«тонкий launcher» не обязателен: Java может запускать бинарь напрямую, а конфиг
профиля — читать из файла.

## Лицензия и установка

- Python-пакет `camoufox` — **MIT** (`License: MIT` в `METADATA`, `licenses/LICENSE`).
- Сам браузер — **MPL-2.0** (README пакета: «The browser itself is MPL-2.0»). Для
  локального запуска и распространения образа этого достаточно; обязательств
  AdsPower-овского ToS нет.
- Бинарь ставится `uv tool install camoufox` + `camoufox fetch`; активная сборка
  пишется в `~/.cache/camoufox/config.json` (`active_version`). Пин — эта строка, а не
  «последняя»: сборка бета-версии Firefox без пина обновится молча.
- Вес: сборка `158.0.1-beta.41` — это отдельный Firefox, ~2,4 ГБ распакованного.

## Что не проверено и переносится в #268–#271

- Доля отказов на **резидентном** прокси и на боевом классе адресов.
- Второй egress-адрес и решающая пара «VPS против VPS».
- `headless="virtual"` и `virtual-gpu`: стоимость, стабильность, требования к `Xvfb`.
- Долгая нагрузка (часы) и поведение при устойчивом 429/498.
- Повторный запуск профиля с сохранённым preset-dict **через прокси** (здесь проверена
  стабильность без прокси).
- geoip-режим: без `geoip=True` Camoufox предупреждает, что при прокси рекомендует его;
  timezone в замере осталась `Europe/Moscow`, что для датацентрового адреса в РФ
  согласовано, но не проверено для других адресов.
