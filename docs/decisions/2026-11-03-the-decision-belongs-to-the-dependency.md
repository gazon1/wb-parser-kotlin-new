## Context

Таблица решений по major-зависимостям была ключом номером pull request'а:

- краулер: `config/gates/dependency-decisions.tsv` (`97	deferred	eclipse-temurin 22 → 25: …`);
- витрина: `config/dependency-decisions.tsv` (`35	deferred	typescript 5.6 → 7: …`).

Номер PR — это не идентичность решения, а запись о конкретном заходе. Как
только dependabot открывает **следующий** PR по той же зависимости, номер
меняется — и записанное решение перестаёт существовать: таблица молчит, и
«решения нет» ничем не отличается от «решение принято, но потерялось».

Живой случай в краулере: решение `eclipse-temurin 22 → 25` отложено под PR #97
(взяли и сломали образ — сборка просит `jvmToolchain(22)`, а образ с JDK 25 её
не обеспечил; вернулись в 22). Dependabot открыл новый PR **#169** с тем же
бампом — и обязательная проверка `static` на нём красная:

```
the images carry the JDK the build asks for (exit 1)
```

Решение при этом есть и было принято осознанно. Поломки настоящей нет —
есть решение, которое не пережило новый номер PR. Но красное проверки не
отличить от поломки, и обход dependabot'а каждый раз начинает разговор заново:
«решения нет — человек решает», хотя человек уже решил.

То же в витрине: `typescript 5.6 → 7`, `vitest 2 → 5`, `tailwindcss 3 → 4`
отложены с причинами, и каждый следующий re-open dependabot'а начинается с
нуля.

## Idea

1. **Оставить ключом номер PR и добавить переход «решение по прошлому PR по той
   же зависимости».** Отклонено: это правило «как найти прошлый PR по той же
   зависимости» — это вторая копия той же таблицы, и она устаревает отдельно от
   неё. Плюс решение всё равно привязано к заходу, а не к зависимости.
2. **Ключом сделать пару версий (`eclipse-temurin 22 → 25`).** Отклонено: пара
   версий — это не то, о чём решение; решение может быть «этот major отложен
   до миграции», а миграция — это не версия.
3. **Ключом сделать зависимость, а номер(а) PR оставить атрибутом записи.**
   (выбрано)

## Decision

**Решение принадлежит зависимости. Номер pull request'а — часть причины, а не
ключ.**

Таблица решений переезжает на схему «зависимость → решение»:

```
<зависимость>\t<решение>\t<диапазон версий>\t<почему>
```

- **зависимость** — имя, которым dependabot называет обновление:
  `eclipse-temurin`, `actions/setup-java`, `typescript`, `io.ktor:ktor-client-core`.
  В конце имени может стоять `*` — «любая зависимость с таким началом»
  (`io.ktor:*`, `org.springframework:*`): один major едет целым семейством
  артефактов, и перечислять их по одному — таблица, которую никто не
  поддержит;
- **решение** — `taken` (взято), `deferred` (отложено), `unnecessary`
  (ненужно);
- **диапазон версий** — `22 → 25`: к какому бампу относится решение. `*` —
  решение не привязано к конкретному бампу;
- **почему** — причина по-русски, и в ней живёт номер(а) PR, которыми решение
  было принято: «PR #97 и PR #169 — тот же бамп, новый номер».

Таблица остаётся TSV и падает громко: незнакомое слово в графе «решение», пустая
причина, пустое имя или нечитаемый диапазон версий — это поломка таблицы, а не
молчание. Пустая и отсутствующая таблица поломкой не являются.

**Чтение — по зависимости.** `python3 scripts/dependency_decision.py
<зависимость> [<из> <куда>]` отвечает, что решено по этой зависимости; если
решение привязано к конкретному бампу, оно находится только по этому бампу.
Диапазон в запросе — это диапазон из тела pull request'а, и «22 → 25» не
находит решение «25 → 26».

**Зависимость читается из тела pull request'а.** dependabot пишет в теле
собственные слова: `Bumps eclipse-temurin from 22-jre to 25-jre.` для одной
зависимости и таблицу `| [имя](ссылка) | \`было\` | \`стало\` |` для группы.
Branch name (`dependabot/docker/eclipse-temurin-25-jre`) для этого не годится:
версия в нём не отделена от имени (`eclipse-temurin-25-jre`), и «имя
зависимости» из него приходилось бы угадывать. Тело — это то, что dependabot
пишет сам и что уже лежит у workflow'а под рукой.

**Обход dependabot'а спрашивает решение по зависимости PR, а не по номеру.**
`python3 scripts/dependency_decision.py --pull-request <файл-тела>` читает
зависимость из тела и находит решение по ней. Если зависимость прочитать не
удалось — это `unknown`, и workflow говорит об этом отдельно: решение могло
быть, и его не нашли.

**Гейт, который проверяет согласие версий, объясняет записанное решение.**
`scripts/ci/check-docker-jdk.py` спрашивает таблицу решений по
`eclipse-temurin` и по диапазону «старая → новая», который он и так видит:
сборка просит одну версию, образ несёт другую. Если по этой зависимости
записано `deferred` с причиной — гейт печатает «решение отложено: <причина>» и
**не падает**: расхождение ожидаемое, оно и было решено. Настоящее расхождение
без записанного решения — по-прежнему падение.

Витрина использует ту же схему ключа: тот же формат строки, тот же скрипт, тот
же ключ «зависимость». Решения, которые выглядят по-разному в двух
репозиториях, — это два набора правил вместо одного.

## Rationale

Решение о major-обновлении — это ответ на вопрос «что мы делаем с этой
зависимостью», а не «что мы делаем с этим pull request'а». Pull request — это
заход: dependabot открывает новый для той же зависимости при каждом цикле, и
он открывается снова и снова, пока зависимость не решена. Ключ, который меняется
при каждом цикле, не может быть ключом решения: решение переживает номер.

Разница не косметическая. Пока решение живёт под номером:

- гейт, который проверяет согласие версий, падает на следующем же PR по той же
  зависимости — и падение выглядит как новая поломка, хотя это старая, уже
  решённая;
- обход dependabot'а говорит «человек решает» о вопросе, который человек уже
  решил, — и это молчание, которое стоит дорого: список major'ов растёт, и
  причины отложенных решений теряются вместе с номерами.

Ключ по зависимости делает ровно то, что нужно: решение, принятое однажды,
находится для следующего PR по той же зависимости, и гейт говорит «решение
отложено: <причина>» вместо падения без объяснения.

Диапазон версий в записи — не украшение, а граница: решение «typescript 5.6 → 7
отложено» не отвечает за «typescript 6 → 7», потому что это другой вопрос.
Запись без диапазона (`*`) отвечает за любой бамп этой зависимости — так
записывают решения, которые не про версии, а про саму зависимость.

Префиксное имя (`io.ktor:*`) — потому что major едет семейством: перечислять
`ktor-client-core`, `ktor-client-cio`, `ktor-http` и ещё четыре по одному —
это таблица, у которой через месяц не будет соответствия реальности.

## Consequences

- **Always** записывать решение по зависимости, а номер(а) pull request'а —
  оставлять в причине.
- **Never** ключить решение номером pull request'а: номер меняется при каждом
  цикле dependabot'а, и решение перестаёт находиться.
- **Always** спрашивать решение по зависимости: и в обходе dependabot'а, и в
  гейтах, которые проверяют согласие версий.
- **Always** объяснять гейтом записанное решение, а не падать молча: решение
  `deferred` с причиной — это объяснение, а не ошибка.
- **Never** прощать гейту расхождение без записанного решения: никто не
  решал, что образ может нести не ту версию.
- **MUST** читать зависимость из тела pull request'а: это то, что dependabot
  пишет сам, и то, что уже есть у workflow'а.
- **MUST** падать громко на нечитаемой таблице решений: решение, которое
  никто не может прочитать, не решение.
- **Always** держать одну и ту же схему ключа в краулере и в витрине.
