## Context

Два наблюдения, которые накопились вместе:

1. `wb_catalog_targets.yaml` был в `.gitignore`. Файл — это список целей краула: какие
   каталоги WB мы вообще собираем. Развёртывание, у которого нет этого файла, не может
   сказать, «краул полный» или «краул потерял половину каталогов»: в базе просто меньше
   строк. И файл не менялся в репозитории, поэтому правки каталога не попадали в историю
   коммитов и не переживались вместе с кодом.
2. `scraped_items` — таблица с историей: одна строка на пару (цель, товар, цена), и цена
   входит в `content_hash`. Изменение цены пишет **новую** строку, поэтому у товара
   несколько строк с разными ценами. «Сколько сейчас стоит товар» — это вопрос, на
   который таблица не отвечает без просмотра по времени.

## Idea

- Хранить каталог целей в БД как единственный источник истины (уже так) и не версионировать
  YAML.
- Версионировать YAML и добавить в него токены каталогов — тогда «какие цели мы
  краулим» видно в diff'е коммита.
- Сделать представление «последнее наблюдение на product_id» таблицей, обновляемой при
  записи.

## Decision

- `wb_catalog_targets.yaml` **больше не игнорируется** и версионируется в репозитории.
  Файл не содержит секретов: только публичные id каталогов WB, названия, пути и токены
  меню.
- Добавлена миграция `V5__catalog_search_query_and_latest_view.sql`:
  - колонка `crawl_targets.wb_search_query` — токен меню, выбирающий категорию в API WB;
  - представление `latest_product_observations` — последняя строка по каждому
    `product_id` (`DISTINCT ON (product_id) … ORDER BY product_id, scraped_at DESC, id DESC`);
  - индекс `ix_scraped_items_product_latest` под это представление.
- `level` в `category_mappings` документирован: строка — это собственный предмет товара
  (`level = 0`), а родитель в ней **ссылается** (`parent_node_id` / `node_name`), а не
  материализуется отдельной строкой: API присылает ровно два id.

## Rationale

Каталог целей — часть описания системы, а не локальная настройка: без него нельзя
проверить, что краул собрал всё. Разница между «каталог сократился» и «каталог изменился»
должна быть видна в истории коммитов.

Представление, а не вторая таблица: источник истины — `scraped_items`, и его история
цен нужна. Дублировать её в отдельную таблицу означало бы рассинхронизацию.

`DISTINCT ON` с явным `id` в порядке — чтобы результат представления был
детерминированным: представление, возвращающее разные строки на двух одинаковых запросах,
— это представление, о котором нельзя рассуждать.

## Consequences

- **Always** держать `wb_catalog_targets.yaml` в репозитории и прогонять
  `scripts/wb-catalog/enrich_catalog_queries.py` перед загрузкой в БД.
- **Never** полагаться на YAML как на единственный источник целей: в БД они всё равно
  лежат в `crawl_targets`, а YAML — это их источник и версия.
- `latest_product_observations` отдаёт по строке на товар; историю цен по-прежнему видно
  в `scraped_items`.
