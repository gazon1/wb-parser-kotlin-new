## Context

`EgressRouter.kt` — 408 строк после решения #114 («одно состояние egress-группы») — держал
вместе маршрутизацию и типы состояния:

- `DownloadOutcome` — как закончился один запрос (`Success` / `Antibot` / `Error`);
- `EgressAttribution` — что раннер вправе спрашивать у адресной стороны;
- `EgressRouterConfig` — настройки роутера: пороги circuit'а, окно здоровья, порог отказа.

Роутер к этому моменту стал фасадом над тремя решениями: `EgressPacerRegistry` (кто
обслужит следующий запрос), `GroupCircuit` (когда адрес остывает) и `GroupHealth` (кому
можно верить как свидетелю). Каждое из них уже живёт в своём файле — так же, как
`EgressGroupState`, `EgressGroupStates` и `EgressCircuitState`, вынесенные решением #114.

Типы состояния остались в файле роутера. Роутер ими **не пользуется** как маршрутизацией:
`DownloadOutcome` читают `GroupHealth`, `GroupCircuit` и счётчики, `EgressAttribution`
читает раннер, `EgressRouterConfig` читает конфигурация развёртывания. В файле, который
назван «роутер», лежало то, что он только раздаёт.

Цена не в числе строк, а в ответе на вопрос «что этот файл решает». У файла было три
ответа, и ни один из них не был «маршрутизация».

## Idea

1. **Оставить как есть.** Отклонено: файл продолжает держать решения, которые к нему не
   относятся, и следующий читатель ищет их именно здесь.
2. **Собрать типы в один файл (`EgressTypes.kt`).** Отклонено: файл на несколько типов
   повторяет ту же болезнь, только в меньшем масштабе — у файла снова несколько ответов,
   и добавление третьего типа не требует нового решения.
3. **По одному файлу на тип, имя файла — имя типа (выбрано).** Файл тогда отвечает на
   один вопрос, и вопрос виден в его имени.

## Decision

**У каждого типа состояния — свой файл, названный по типу.** В пакете
`ru.wbparser.infra.http`:

- `DownloadOutcome.kt` — как закончился запрос;
- `EgressAttribution.kt` — что раннер спрашивает у адресной стороны;
- `EgressRouterConfig.kt` — настройки роутера.

**В `EgressRouter.kt` остаётся маршрутизация.** Роутер выбирает группу, ведёт её книги и
переводит словарь circuit breaker'а в словарь кодовой базы. Всё, что описывает
состояние, живёт в своих файлах, и каждый такой файл говорит в своём KDoc, какое решение
он держит.

**`AllEgressGroupsUnavailable` остаётся в файле роутера.** Это не тип состояния: это
отказ самой маршрутизации («никто не может обслужить запрос»), и он живёт рядом с
`borrow`, который его бросает.

**Это перенос решения, а не новая логика.** Имена, сигнатуры, значения по умолчанию и
поведение прежние; изменён только адрес объявления. Проверка — те же тесты, что и до
переноса.

## Rationale

Роутер — фасад над тремя решениями, и это хорошо: решение о том, «кто обслужит следующий
запрос», принимается в одном месте. Но фасад, в котором лежит ещё и словарь состояния,
перестаёт быть фасадом: читатель, ищущий «как здесь считается отказ», находит enum в
файле про выбор группы и решает, что отказ — это часть выбора группы.

Разделение по решению — уже принятое в этом репозитории правило (ADR «крупные классы
делятся по решению, которое они держат»): `WbCatalogRequest` разошёлся на
`WbCatalogRequest` / `WbCatalogApi` / `WbCatalogFetchScript`, и каждый файл отвечает на
свой вопрос. Здесь то же самое, только на один шаг меньше: не класс делится на части, а
файл делится на файлы по типам, которые в нём объявлены.

По одному файлу на тип — потому что дальше файлы начинают добавляться: следующее
решение (метрики, цепи) добавит свой тип, и если типы снова свалятся в один файл, через
месяц будет тот же разговор. Имя файла совпадает с именем типа — потому что вопрос
«что здесь решается» должен читаться без открытия файла.

Что осталось за кадром: `GroupHealth`, `GroupCircuit` и `EgressPacerRegistry` живут в
своих файлах уже сейчас — они были вынесены вместе со своими решениями. Этот перенос
дописывает то, что осталось: типы состояния, которыми эти решения пользуются.

## Consequences

- **Always** держать в файле роутера только маршрутизацию: выбор группы, её книги и
  перевод состояния circuit'а в словарь кодовой базы.
- **Never** объявлять в файле роутера типы состояния (`DownloadOutcome`,
  `EgressAttribution`, `EgressRouterConfig` и подобные): у каждого типа — свой файл,
  названный по типу.
- **Always** писать в KDoc типа, какое решение он держит: файл без этого ответа
  повторяет ту же проблему в меньшем масштабе.
- **Never** менять поведение вместе с переносом: перенос решения не должен двигать
  значения по умолчанию, подписи и границы.
