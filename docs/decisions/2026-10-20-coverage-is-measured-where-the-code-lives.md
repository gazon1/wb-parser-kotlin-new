## Context

Модуль `tests` — интеграционные тесты (Testcontainers, реальная БД, гейт старта приложения).
Его тесты выполнялись, но **не учитывались** в покрытии: `CrawlRunner` (153 строки) —
код, который пишет в базу, держит блокировки, считает страницы и товары, — показывал
**0 из 153** покрытых строк. То же для `TargetQueries` (68) и `SavedItemQueries` (71).
Ровно те классы, где ошибка стоит дорого, были не видны гейту.

Первая попытка была «включить в отчёт модуля `tests` пакеты зависимостей» — отчёт остался
пустым, и я записал в ADR, что kover 0.9.11 не умеет агрегировать покрытие зависимого
модуля. **Это было неверно.** Kover умеет: root-проект объявляется *merging module* через
зависимости `kover(project(...))`, и его отчёт становится объединением классов всех
указанных модулей и покрытия, которое дали их собственные сьюты. Механизм называется
merged report, и он был доступен в той же версии плагина.

Ошибка была не в kover, а в том, что я искал не там: отчёт модуля по определению содержит
только классы этого модуля, и никакой фильтр туда чужие классы не добавит.

## Idea

1. Отчёт модуля `tests` с фильтрами на чужие пакеты. Отвергнуто: так не работает.
2. Перенести все интеграционные тесты в модули, которым принадлежит код. Частично верно,
   но тесты, проверяющие схему миграций, без них не собираются.
3. **Merged report на уровне root + тесты рядом с кодом.** Выбрано.

## Decision

**Root-проект — merging module.** В корневом `build.gradle.kts`:

```kotlin
dependencies {
    kover(project(":app"))
    kover(project(":wbparser"))
    kover(project(":tests"))
}
```

Его `koverXmlReport` даёт отчёт по всему репозиторию: 23 пакета, 76,8 % строк. Гейт
покрытия получил третью строку — `merged 75`.

**Строки floors остаются и по модулям.** `app 32`, `wbparser 70` — модульные отчёты
показывают, где именно просело покрытие; merged показывает состояние репозитория.

**Тест живёт рядом с кодом, который он проверяет.** `TargetQueriesPostgresTest` и
`CrawlRunnerPostgresTest` переехали в `wbparser`, чистые юнит-тесты пайплайна,
интерпретаторов и правил фильтрации — тоже. Модуль `tests` отошёл к тому, что действительно
нуждается в миграциях Flyway: гейт схемы, старт приложения, интеграционные сценарии.

**Схема в тестах wbparser строится из Exposed-модели** (`SchemaUtils`), а её соответствие
миграциям проверяет `SchemaDriftTest` в модуле `tests`. DDL не дублируется.

## Rationale

Гейт покрытия полезен ровно настолько, насколько измеряет то, что страшно оставлять
непокрытым. Класс, который пишет в базу, страшно оставлять непокрытым — и он был именно
таким, причём не из-за отсутствия тестов: тесты были, они просто не считались.

Merged report закрывает это без переписывания тестов: любой сьют любого модуля теперь
учитывается. А перенос тестов к коду нужен для другого — чтобы в модуле, где код, лежали
и тесты, которые его проверяют: правило, которое можно соблюдать, а не только измерить.

## Consequences

- **Always** объявлять merged report в root-проекте: без него отчёт модуля `tests`
  остаётся пустым, а гейт не видит ни одного интеграционного теста.
- **Never** считать, что отчёт модуля содержит классы зависимостей: он содержит только
  свои. Чужой код попадает в отчёт через merging module, а не через фильтр.
- **Always** писать интеграционный тест рядом с кодом, который он проверяет, а не в
  отдельном модуле «интеграционных» тестов.
- **Never** дублировать DDL в тестах: схема строится из модели, соответствие миграциям
  проверяется отдельным тестом на дрейф.
- **Always** поднимать floor покрытия тем же коммитом, который поднял покрытие
  (`./scripts/raise-kover-floor.py`).
