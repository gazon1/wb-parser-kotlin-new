date: 2026-10-14

## Context

The tech-debt plan identified two purity violations inside `Pipeline.run()`:

1. **`UUID.randomUUID()` in pagination task IDs** — `idGen` was hardcoded in `buildParserPipeline`
   and never overridden from `CrawlRunner`, making pagination task IDs non-reproducible.
2. **`delay()` inside `stageWithRetry` and `saveOne`** — flagged as "impure".

## Ideas Considered

### For idGen

- **Inject via `Pipeline` constructor** (chose this) — `Pipeline` already accepts `idGen: () -> String`
  with a default of `UUID.randomUUID()`. `CrawlRunner.runTarget()` now passes it through, and the
  start task ID is also generated by the same `idGen`. Tests can inject a deterministic counter.
- Leave it hardcoded — rejected: non-reproducible crawls prevent debugging.

### For delay()

- **Move delay outside the pipeline** — suggested by the tech-debt note.
  Rejected: `delay()` implements the back-off wait between retry attempts. It **must** suspend
  the current coroutine; there is no "external scheduler" in this architecture. The retry loop
  is correctly implemented as a `while (true) { result = stage.invoke(input); if (result !is Retry) return result; delay(...); }`.
  This is the standard suspend-based retry pattern. The "impurity" here is a **necessary
  part of the retry contract** — unlike `UUID.randomUUID()` which is truly non-deterministic.
  The ADR rule "never call delay() inside a Stage" is about delay-called stages (e.g. a
  `delay`-based rate-limiter), not about the retry machinery itself.

## Decision

1. `CrawlRunner.runTarget()` now accepts `startTaskIdGen: () -> String` with default
   `UUID::randomUUID`, and passes it both as the initial `Crawling` task ID and as
   `idGen` to `buildParserPipeline`. This makes pagination task IDs injectable and
   the start task ID deterministic-injectable.

2. `delay()` calls in `stageWithRetry` and `saveOne` are **intentional and correct** — they
   implement the suspend-based back-off retry pattern. The ADR rule "never call `delay()` inside
   a Stage" applies to **stage functions** (download, parse, etc.), not to the pipeline's
   internal retry orchestration.

## Consequences

- `Pipeline.run()` is still not referentially transparent due to `delay()` in retry loops,
  but this is a fundamental property of any suspend-based retry implementation and does not
  affect testability or debuggability.
- Pagination task IDs and the start task ID are now explicitly controllable — critical for
  deterministic integration tests.
