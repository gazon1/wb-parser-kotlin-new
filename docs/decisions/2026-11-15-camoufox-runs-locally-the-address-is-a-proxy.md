## Context

Umbrella #266 заменяет AdsPower локальным Camoufox: парсер и браузер на рабочей машине,
VPS — только proxy endpoint. #267 требовал проверить эту схему **до** правок
production-кода: даёт ли несколько persistent-профилей измеримый прирост полезной
скорости при контролируемой нагрузке, и какие у схемы ограничения.

Замер (`docs/operations/camoufox-local-run/2026-11-15-camoufox-local.md`, сырые JSON
рядом) снят на 16-ядерной машине, Camoufox 0.5.9 / сборка `158.0.1-beta.41`,
Playwright 1.63.0, `headless=True`, каталог 9467 через `__internal/u-search` из страницы.

Что выяснилось и чего не ожидалось:

- **Пропускная способность растёт почти линейно до 4 профилей** — 1439 / 2771 / 3322 /
  4584 товаров в минуту на прямом адресе (1,00 / 1,93 / 2,31 / 3,19 от одного профиля) и
  1277 / 2443 / 3733 / 4347 через VPS (1,00 / 1,91 / 2,92 / 3,40).
- **`user_data_dir` не сохраняет отпечаток.** Один и тот же каталог, запущенный дважды
  без явного конфига, дал разные UA, platform, screen и WebGL. `fingerprint_preset=True`
  тоже рандомизирует. Стабильность даёт только **явный preset-dict**.
- **Playwright не поддерживает SOCKS5 с логином и паролем** — падает с «Browser does not
  support socks5 proxy authentication». HTTP-прокси с Basic-auth работает.
- **Camoufox запускается без Python-пакета**: сырой `firefox.launch(executable_path=…,
  env={CAMOU_CONFIG_*})` даёт 200 и 100 товаров. Пакет — только подготовка launch options.
- **Датацентровый адрес не отвергается на уровне API**: HTML-переход отвечает 498, а API
  из страницы — 200. Повторяет правило umbrella: статус навигации ≠ доступность API.
- Отказ приходит **пачкой по счёту запросов сессии** (первый отказ на 13–19-м запросе),
  и с ростом числа профилей на одном адресе сдвигается раньше — как и в замере
  2026-10-21.
- Ресурсы: ~1,05 ГБ RSS на профиль, 0,3–1,2 ядра на 1–4 профиля.

Лицензии: Python-пакет MIT, браузер MPL-2.0.

## Idea

- (1) Оставить AdsPower как browser runtime и продолжать пользоваться его CDP-подключением.
- (2) Локальный Camoufox, запускаемый Python-обёрткой (сайдкар), Java подключается к
  нему по websocket (`launch_server`).
- (3) Локальный Camoufox, запускаемый из Java напрямую; конфиг профиля — файл в
  репозитории/на диске; прокси назначается профилю.
- (4) Локальный Camoufox плюс отдельный генератор отпечатков в рантайме.

## Decision

**Номер (3): Java запускает Camoufox напрямую, отпечаток — сохранённые данные профиля,
прокси назначается профилю и не меняется.**

Пункты решения, каждый — из измеренного факта:

**Прямой запуск из Java, без Python-обёртки.** Замер показал, что весь конфиг — это путь
к бинарю, `CAMOU_CONFIG_<n>` (JSON, нарезанный по 32767 байт), `CAMOU_PREFS_<n>` и
`FONTCONFIG_FILE`. Playwright Java умеет `setExecutablePath` и `setEnv`. Тонкий launcher
(2) не нужен, потому что нужен был бы только для генерации отпечатка — а отпечаток
хранится, а не генерируется.

**Отпечаток считается один раз на профиль и хранится.** `user_data_dir` его не хранит:
два запуска одного каталога дают две разные identity. Значит, per-profile JSON — часть
конфигурации профиля, а не кэш: он лежит рядом с профилем, читается при запуске и не
перегенерируется. Пункт (4) не нужен: генерировать нужно ровно один раз, на этапе
создания профиля, а не в рантайме.

**Endpoint должен принимать браузер, то есть SOCKS5 без пароля или HTTP с Basic-auth.**
Playwright отвергает аутентифицированный SOCKS5 («Browser does not support socks5 proxy
authentication»). Сегодняшний danted объявлен с `socksmethod: username`, то есть
**требует** пароль, — такой endpoint браузер не примет вообще. Это не деталь замера, а
изменение контракта: раз ограничение по адресу уже задано в самом прокси
(`client pass from <адрес краулера>/32`), пароль для SOCKS5 избыточен, и endpoint либо
переводится на `socksmethod: none` при сохранённом CIDR, либо получает HTTP-слушатель.
Краулер к прокси сам не ходит, поэтому прокси — целиком ответственность запуска браузера.

**Прокси назначается профилю и не меняется.** Смена адреса — новая личность
(ADR `2026-10-23-a-changed-address-is-a-new-identity`), и отпечаток, сохранённый на
профиле, к другому адресу не переезжает молча.

**`headless=True` остаётся, пока `virtual` не измерен.** `True` прошёл замер;
`virtual`/`virtual-gpu` требуют `Xvfb` (или Xorg и GPU), а его на машине нет. Режим не
выбирается по рекомендации — он выбирается по измерению, которого пока нет.

## Rationale

**Почему прямое управление, а не launcher.** Python-сайдкар добавляет рантайм, который
придётся ставить, пинить и держать живым, — и всё это ради функции, которая нужна один
раз на профиль. Замер показал, что без него работает всё, включая антибот: запуск
сырым Playwright дал тот же результат, что и запуск обёрткой. Держать процесс, который
нечего делать в рантайме, — это цена без выгоды.

**Почему отпечаток — данные, а не поведение.** Persistent-профиль обещает «тот же
браузер», но хранит только cookies и storage: identity рисуется при каждом старте.
Если её не сохранить, рестарт краулера — это новый браузер с того же адреса, то есть
ровно то, что egress-группы должны исключать. Отпечаток, лежащий файлом, делает рестарт
незаметным для сайта — и, что важнее, **проверяемым**: файл можно сравнить, а
сгенерированное на лету поведение — нет.

**Почему прокси профиля, а не адрес группы.** Бюджет WB считается сессией, а сессия
живёт в профиле (`docs/CONTEXT.md`). Профиль, который при каждом запуске получает
другой адрес, выглядит как сессия, которая переезжает, и сравнивать такие прогоны
нельзя. Один профиль — один адрес — один отпечаток: тогда измерение говорит об адресе,
а не о переезде.

**Что замер не решил и почему это честно.** Доля отказов на резидентом адресе,
решающая пара «VPS против VPS», `virtual`-режим и долгая нагрузка — не проверены.
Замер отвечает на вопрос «даёт ли локальная схема прирост» (да, почти линейный до 4
профилей), но не на вопрос «какой безопасный предел на боевом классе адресов». Второй
вопрос требует второго адреса и ≥3 повторов по протоколу — это отдельный блок, а не
побочный результат этого.

## Consequences

- **Always** хранить отпечаток профиля явным preset-файлом: `user_data_dir` его не сохраняет, и без файла рестарт — это новый браузер с того же адреса.
- **Never** полагаться на `fingerprint_preset=True` для стабильности: он выбирает случайный пресет при каждом запуске, и identity расходится.
- **MUST** запускать Camoufox из Java напрямую (`setExecutablePath` + `setEnv` с `CAMOU_CONFIG_<n>`): Python-обёртка нужна для генерации отпечатка, а он хранится, а не генерируется.
- **Never** настраивать аутентифицированный SOCKS5 в Playwright: он отвергается («Browser does not support socks5 proxy authentication»); endpoint либо без пароля с ограничением по CIDR, либо HTTP с Basic-auth.
- **Always** назначать прокси профилю и держать его неизменным: смена адреса — новая личность (ADR `2026-10-23-a-changed-address-is-a-new-identity`).
- **Never** считать статус навигации проверкой антибота: датацентровый адрес даёт 498 на HTML и 200 на API из страницы.
- **Always** считать отказ по счёту запросов сессии, а не по темпу: первый отказ ложится на 13–19-й запрос и сдвигается раньше с ростом числа профилей на одном адресе.
- **MUST** останавливать прогон после нескольких отказов подряд, а не добивать фиксированную квоту: иначе измеряется место, где кончился счётчик, а не полезная работа.
- **Never** выбирать `headless`-режим по рекомендации: `True` измерен, `virtual`/`virtual-gpu` требуют `Xvfb` и отдельного замера.
- **Always** пинить сборку Camoufox (`~/.cache/camoufox/config.json` → `active_version`): это бета-сборка Firefox, и без пина она обновится молча.
- **MUST** держать отпечаток стабильным на профиль: два разных отпечатка с одного адреса выглядят как два браузера за одним IP — ровно то, чего egress-группы избегают.
